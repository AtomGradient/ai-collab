## 3. 当前实现到底完成了什么

已审 target `bcc11bbc4c338575e02d8592bea903cde5845568` 完成：

1. Host 只消费 versioned capability descriptor；普通 Codex/Claude CLI 由 Harness supervisor 启动。vendor session identity 与 exact resume 是显式可选 capability，当前两个真实 driver 均声明 `vendor_lifecycle_surface: none` 与 `explicit_recreate`。
2. supervisor 通过 private token/generation ACK 固定 supervisor、launch-root 与 owned process group；iTerm `Window.async_create()` 返回 exact window/tab/session，session `jobPid` 只有在它是 launch-root 或经 PPID chain 证明的 live descendant、且 process group 匹配时才能建立 presentation binding。Host 不按产品名、process name、cwd、role、recent window/session 或私有 vendor store 猜测。
3. create response 在 new-identity、marker 与 topology 初始化期间均由 exact handle 跟踪；初始化异常立即 bounded close。无法证明 cleanup 时进入 unresolved failure，不能由 `item.window is None` 推导成功。
4. vendor child 环境使用 closed allowlist；endpoint override、Node/Python/DYLD injection 与 XDG config override 不从调用 pane 继承，隔离结果由 supervisor ACK 实测返回。
5. runtime verifier 的七个 registry params 均进入实际判定；capability descriptor 使用 exact key set 并重算 digest；incompatible request 有 before/after isolation witness。
6. owned cleanup 先 quiesce exact child 并写 private status，同时让 supervisor 保持 exact terminal session；随后 ownership marker round-trip、exact Python `Window.async_close()` 成功与独立 native visibility audit 必须同时成立。AppleScript 只做 exact identity equivalence/只读审计，不执行关闭、不进入 Host/runtime contract、不使用 name/recent/delta。
7. supervisor 在 presentation close 后若仍存活，必须收到 release 并写 private ACK；若它已在成功的 exact close RPC 后退出，receipt 只披露该路径。没有成功 close RPC 时，Python/native model absence 或 supervisor absence 都不能替代 cleanup success。
8. Host 独立观测 ACK launch-root 与 accepted foreground PID 在 quiesce 后和最终 teardown 后均 absent，不把 supervisor 自报的 status 单独当成 process cleanup 证明；任一 owned process 未 quiesce 且仍存活时拒绝关闭 presentation，并给出 portable refusal/failure reason。
